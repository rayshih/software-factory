這是一場 30 天的 speed run。過去幾個月 Ray 已經做過一版。這次實驗用現成工具黏起來，從零重做，看 30 天能走多遠。每週公開進度、成本和哪裡壞掉。

AI agent 已經寫得出程式碼。團隊缺的是包在外面的那座工廠：佇列、執行控制、失敗後怎麼復原、CI 驗證、人工 review、稽核軌跡，以及成本看得到。Software Factory 是這一層控制。它接現成的基礎設施，而不是再做一個 agent。

你負責許願跟驗收，其他交給 AI。

每一次 merge 都由人核准。沒有自動 merge。Coding 正在做。另外三項是計畫。目前都還不能用。

  1. 進行中

    Coding

    你描述問題，AI 寫 code。

  2. 計畫中

  3. 計畫中

02 — 怎麼運作

GitHub Issue 進來，可以 review 的 PR 出去。

有標籤的 GitHub Issue，會從 GitHub App 進來。控制層先把它存下來。Trigger.dev 負責排隊，限制同時跑幾件，也處理重試。Anthropic Managed Agent 在 sandbox 裡工作。跑完會開 branch 和 PR，GitHub Actions 跑 CI，然後由人 review。

GitHub Issue → GitHub App / webhook → 控制層（Postgres）→ Trigger.dev 佇列 → Anthropic Managed Agents sandbox → branch + PR → GitHub Actions CI → 人工 review

  1. 01

    GitHub Issue

    待辦裡一個標好標籤的項目。

  2. 02

    GitHub App

    Webhook 進來。任務以冪等方式存下來。

  3. 03

    Control plane 建造中

    Postgres。決定任務何時跑，並記錄狀態、成本與失敗。

  4. 04

    Trigger.dev

    佇列、全域與各專案的並行上限、重試。

  5. 05

    Managed Agents

    Anthropic 的 session 和 sandbox，含逾時。

  6. 06

    Branch + PR

    一件任務一張 PR。重試不會再開第二張。

  7. 07

    GitHub Actions

    請人 review 之前，先過 CI。

  8. 08

    Human review 一律

    核准、要求修改，或退件。

要求修改會把任務送回佇列。退件會關閉任務，並把失敗記下來。核准才算接受這張 PR。沒有自動 merge。Agent session 沒在動，不代表任務做完了。

04 — 原則

會守住的事，以及這次不會做的事。

原則

  1. 用現成的基礎設施，不自己重做一套。
  2. Agent 的執行環境和控制層拆開。
  3. 每個對外操作都要冪等。
  4. 重試不會開出重複的 PR。
  5. Agent session 閒著，不算任務完成。
  6. 每張 PR 都由人 review。
  7. 成本、人介入了多少、失敗原因，都要留下紀錄。
  8. 絕不在未經授權的專案上跑。

這次實驗不做

  • SaaS 註冊與上手
  • 收費
  • RBAC / SSO
  • 多租戶
  • 自建 agent harness
  • 自建排程器
  • 多模型路由
  • 自動 merge
  • 部署自動化
